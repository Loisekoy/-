# FitTrack Pro 資料庫系統操作手冊與口試準備

版本：2026-10-17
適用程式：`codex生成/php-app`（PHP 8.4+、PDO、正式 PostgreSQL 16）
本手冊目的：說明系統如何運作、20 張應用資料表如何關聯，以及展示或口試時可以如何回答。

> 重要：本文件以目前正式 PHP 版本的 `database/postgres.sql` 為準。早期 React／FastAPI 原型使用的 `plan_id`、`name_en`、`llm_generations` 等欄位不屬於目前正式 Schema，請不要混用。

---

## 1. 先用一句話說明這個系統

FitTrack Pro 是一個「以資料庫為核心」的健身紀錄管理系統：使用者先建立個人資料與訓練偏好，系統或使用者建立課表；開始訓練時，系統把課表內容複製成不可受來源變更影響的場次快照；每完成一組就立即寫入資料庫，最後用歷史紀錄與 Dashboard 統計訓練成果。

系統不是把資料只放在瀏覽器。瀏覽器負責操作介面與計時顯示，PHP API 負責驗證與交易，PostgreSQL 負責長期保存、關聯完整性、併發安全與統計查詢。

```text
使用者瀏覽器
    │ HTTPS / JSON API
    ▼
PHP 8.4 + PDO（認證、商業規則、交易）
    │ DATABASE_URL + TLS
    ▼
PostgreSQL 16（正式：Neon；網站：Render）
```

## 2. 資料庫實際建立在哪裡？

### 2.1 本機開發

目前本機快速預覽使用：

```text
/Users/loise/Documents/資料庫/codex生成/php-app/storage/app.sqlite
```

相關檔案：

| 檔案 | 用途 |
|---|---|
| `database/sqlite.sql` | 本機 SQLite 建表定義 |
| `database/postgres.sql` | 正式 PostgreSQL 建表定義 |
| `database/migrations/` | 舊 Schema 升級與正式環境補強 Migration |
| `bin/setup.php` | 建立／補齊 Seed 與展示帳號 |
| `bin/migrate.php` | 執行既有資料庫升級 |
| `storage/app.sqlite` | 本機實際 SQLite 資料 |

啟動本機版本：

```bash
cd /Users/loise/Documents/資料庫/codex生成/php-app
cp .env.example .env       # 第一次才需要
php bin/setup.php
php -S 127.0.0.1:8080 -t public public/router.php
```

### 2.2 公開網站

正式網站是 Render Web Service，正式資料庫是 Neon PostgreSQL。Render 的環境變數 `DATABASE_URL` 指向 Neon 的連線字串；只要設定了 PostgreSQL URL，`Database.php` 就會使用 `pdo_pgsql`，不會使用本機的 SQLite 檔案。

因此：

- Render 容器重啟不會清掉正式資料。
- `storage/app.sqlite` 只屬於本機測試，不是公開網站資料庫。
- 管理員登入「管理 → 資料庫系統」可查看目前連線 Driver、20 張應用資料表、資料筆數與 25 條外鍵。
- 正式環境的 `DATABASE_URL` 必須使用 TLS，例如 `sslmode=require`；連線字串不可寫入 Git。

## 3. 20 張應用資料表分組

`schema_migrations` 是系統版本紀錄表；以下 20 張是應用資料表，正式 Schema 驗收要求為 20 表、25 條外鍵。

### 3.1 參考資料

| 資料表 | 作用 |
|---|---|
| `training_goals` | 訓練目標，例如 Muscle Gain、Fat Loss、Strength |
| `body_parts` | 身體部位，例如 Chest、Back、Legs、Core |

這兩張是被其他表參照的主資料，名稱不直接複製到使用者資料或課表資料中。

### 3.2 帳號、認證與安全

| 資料表 | 作用 |
|---|---|
| `users` | 使用者姓名、年齡、身高、程度、目標、每週天數、每次時間 |
| `user_auth` | Email、bcrypt 密碼雜湊、帳號啟用狀態；一個使用者一筆 |
| `user_sessions` | 登入 Session、建立時間、到期時間、撤銷時間 |
| `admins` | 管理員資格白名單；只存有管理權限的 `user_id` |
| `login_failures` | 雜湊後 IP 與失敗時間，供 15 分鐘登入限流使用 |

`users` 與 `user_auth` 分離，是因為個人資料和認證資料用途不同；密碼不以明文存在 `users`。

### 3.3 個人設定與體重

| 資料表 | 作用 |
|---|---|
| `user_body_parts` | 使用者想加強哪些部位，以及優先順序 |
| `body_records` | 使用者的體重歷史；同一使用者同一天最多一筆 |

`user_body_parts` 是 User 與 Body Part 的 M:N 關聯表，主鍵是 `(user_id, body_part_id)`。

### 3.4 動作資料庫與版本

| 資料表 | 作用 |
|---|---|
| `exercises` | 動作穩定身份，例如某個 `exercise_id`；也存部位與啟用狀態 |
| `exercise_versions` | 動作名稱、難度、器材、步驟說明、圖片網址的不可變版本 |

修改一個已被課表或歷史引用的動作，不覆蓋舊資料，而是建立新的 `version_no`。這樣歷史紀錄仍能顯示當時的名稱、說明與圖片。

### 3.5 課表規劃

| 資料表 | 作用 |
|---|---|
| `workout_plans` | 課表主檔、使用者、名稱、發布時間、封存時間 |
| `planning_profiles` | 產生課表當下的目標、年齡、身高、體重、程度、天數、時間快照 |
| `planning_profile_body_parts` | 產生課表當下的偏好部位與優先順序快照 |
| `plan_days` | 課表中的 Day 1 至 Day 6 |
| `plan_exercises` | 每個 Day 的動作順序、目標組數、次數、休息、目標重量 |

電腦規劃的 `algorithm_version` 目前是 `rules-v2-randomized`；使用者自訂課表則是 `manual-v1`。

### 3.6 實際訓練與歷史

| 資料表 | 作用 |
|---|---|
| `workout_sessions` | 一次實際訓練，狀態為 `in_progress`、`completed` 或 `cancelled` |
| `workout_session_plans` | 場次對應哪一個課表日；一個場次一筆 |
| `workout_session_exercises` | 開始訓練時建立的動作快照，也可調整本次目標 |
| `workout_sets` | 每個動作的第幾組、重量與次數 |

## 4. 關聯圖：老師最常問的部分

```text
training_goals 1 ─────── N users
                         │
                         ├── 1:1 user_auth ─── 1:N user_sessions
                         │        │
                         │        └── admins（0 或 1 筆，代表管理員）
                         │
                         ├── M:N body_parts
                         │       └── user_body_parts
                         │
                         ├── 1:N body_records
                         │
                         └── 1:N workout_plans
                                 │
                                 ├── 1:1 planning_profiles
                                 │       └── M:N body_parts
                                 │              └── planning_profile_body_parts
                                 │
                                 └── 1:N plan_days
                                         │
                                         └── 1:N plan_exercises ── N:1 exercise_versions
                                                                       │
body_parts 1 ─── N exercises ──────────────────────────────────────────┘

workout_plans / plan_days
        │
        └── 1:N workout_sessions（實際訓練）
                │
                ├── 1:1 workout_session_plans ── N:1 plan_days
                └── 1:N workout_session_exercises
                        │
                        └── 1:N workout_sets
```

### 4.1 關聯基數整理

| 關聯 | 基數 | 為什麼 |
|---|---|---|
| `training_goals → users` | 1:N | 一個目標可以被很多使用者選擇 |
| `users → user_auth` | 1:1 | 每個使用者一組登入認證 |
| `users → user_sessions` | 1:N（透過 `user_auth`） | 同一帳號可有多個登入 Session |
| `users ↔ body_parts` | M:N | 一位使用者可選多個部位，一個部位也可被多人選擇 |
| `users → body_records` | 1:N | 一位使用者有多筆日期體重 |
| `body_parts → exercises` | 1:N | 一個部位有很多動作 |
| `exercises → exercise_versions` | 1:N | 同一動作身份可以有多個不可變版本 |
| `users → workout_plans` | 1:N | 一位使用者可以建立多份課表 |
| `workout_plans → plan_days` | 1:N | 一份課表有多個訓練日 |
| `plan_days → plan_exercises` | 1:N | 一天安排多個動作 |
| `workout_sessions → workout_sets` | 1:N（經過場次動作） | 一次訓練包含多個動作與組數 |

## 5. 從使用者操作到資料庫寫入

### 5.1 註冊與登入

1. 使用者送出姓名、Email、密碼。
2. API 在 `users` 新增個人身份。
3. API 在 `user_auth` 新增 Email 與 bcrypt `password_hash`。
4. 登入成功後建立 `user_sessions`，Cookie 只保存 Access Token。
5. 每次受保護 API 都重新查 Session、帳號啟用狀態與管理員資格。

管理員不是靠 JWT 裡的 `role` 決定，而是即時查詢 `admins`；刪除 `admins` 的列後，原本的 Token 也不能繼續使用管理 API。

### 5.2 編輯個人資料

- 基本資料寫入 `users`。
- 訓練目標以 `users.training_goal_id` 外鍵連到 `training_goals`。
- 偏好部位寫入 `user_body_parts`，由 `priority` 表示順序。
- 體重寫入 `body_records`，不把體重複製到 `users`。
- 完成 Profile 後，資料庫至少保留一筆體重，避免規劃沒有重量快照。

### 5.3 電腦規劃課表

系統先讀取：

```text
users 的目標／程度／天數／可用時間
最新 body_records 體重
user_body_parts 偏好部位
最近幾份課表已使用的 exercise_id
```

接著建立：

```text
workout_plans
planning_profiles
planning_profile_body_parts
plan_days
plan_exercises
```

目前規則式規劃會：

- 依 2–6 天選擇訓練分化。
- 每天安排 3–6 個動作，並計算是否超過可用時間。
- 優先完成八個身體部位的每週覆蓋。
- 同一份課表不重複同一個動作身份。
- 透過隨機排序與最近使用排除，避免連續課表幾乎完全相同。

### 5.4 使用者自訂課表

使用者可自行選擇 2–6 個訓練日、每天名稱、動作、順序、組數、次數與休息秒數。送出後仍會寫入同一組 `workout_plans`、`plan_days`、`plan_exercises`，只是 `planning_profiles.algorithm_version` 為 `manual-v1`。

### 5.5 開始訓練：為什麼要建立快照？

按「開始訓練」時：

1. `workout_sessions` 建立一筆 `in_progress`。
2. `workout_session_plans` 記錄來源課表日。
3. `workout_session_exercises` 複製當下的動作版本、順序、組數、次數、休息與目標重量。

這是本系統最重要的歷史設計。即使之後管理員修改動作、使用者修改課表，已開始的訓練仍保留當時的版本與目標；本次目標調整只改 `workout_session_exercises`，不回寫原課表。

### 5.6 儲存每一組

按「儲存此組」後，`workout_sets` 新增：

```text
workout_session_exercise_id
set_number
weight_kg
reps
```

同一個動作的同一組號重送相同內容會被視為冪等；同組號送不同內容會回 409，修改要走更新 API。畫面上的總訓練時間與休息倒數是前端計時器，但「組數是否真的保存」以資料庫 API 回應為準。

### 5.7 完成、取消、封存與刪除

- 完成訓練：`workout_sessions.status = completed`，寫入 `ended_at`；至少要有一組 `workout_sets`。
- 取消訓練：`status = cancelled`，即使尚未儲存組數也可取消，保留取消歷史。
- 課表封存：設定 `workout_plans.archived_at`，不是永久刪除；歷史仍可查。
- 已完成或已取消的整場歷史刪除，會連帶刪除場次組數，但不刪動作版本與來源課表。

## 6. 資料庫安全與完整性

### 6.1 應用程式層

- PHP PDO 使用 prepared statement 與參數綁定，避免 SQL Injection。
- 密碼使用 PHP bcrypt cost 10，不存明文。
- Access Token 使用 HttpOnly、Secure、SameSite=Strict Cookie。
- 寫入要求檢查同源與 CSRF Token。
- JWT 只放 `sub`、`jti`、`iat`、`exp`，角色不放在 Token 作為授權真相。
- 登入失敗用 HMAC 後的 IP 儲存在 `login_failures`，不保存原始 IP。

### 6.2 Schema 約束與 Trigger

| 保護項目 | 做法 |
|---|---|
| 動作版本不可覆寫 | `trg_exercise_versions_immutable` 阻止 UPDATE／DELETE |
| 同一天不可重複同一動作身份 | `trg_plan_exercise_identity_unique` |
| 場次動作必須屬於同一來源 Day | `trg_session_exercise_snapshot_guard` |
| 完成 Profile 至少保留一筆體重 | `trg_body_records_keep_last` |
| completed 場次至少一組 | 三個 deferred constraint trigger |
| 進行中來源課表不可修改 | `trg_lock_active_workout_plan`、`trg_lock_active_plan_day`、`trg_lock_active_plan_exercise` |
| 同一使用者最多一個進行中場次 | PostgreSQL partial unique index `uq_workout_sessions_user_active` |

老師若問「為什麼不只靠前端檢查？」可以回答：前端檢查只能防止正常操作，無法防止 API 重送、兩個 Worker 同時寫入或直接 SQL；所以關鍵規則必須在資料庫再保護一次。

## 7. 正規化、索引與交易的回答方式

### 7.1 正規化

- 1NF：多個偏好部位拆到 `user_body_parts`，不是用逗號字串塞在一欄。
- 2NF：複合主鍵表的欄位依賴完整主鍵，例如 `user_body_parts` 的 `priority` 依賴使用者與部位組合。
- 3NF：目標名稱、部位名稱、動作版本內容各自放在主資料表，不在多張交易表重複保存。
- 例外的快照欄位是刻意的歷史設計，不是忘記正規化；它保存「當時狀態」，避免歷史被現在資料改寫。

### 7.2 重要索引

- `user_sessions(expires_at)`：清理過期 Session。
- `login_failures(ip_hash, failed_at DESC)`：登入限流滑動視窗。
- `body_records(user_id, record_date DESC, body_record_id DESC)`：抓最新體重。
- `exercise_versions(exercise_id, version_no DESC)`：抓最新動作版本。
- `workout_plans(user_id, created_at DESC)`：列出使用者課表。
- `workout_sessions(user_id, started_at DESC)`：歷史與 Dashboard。
- `workout_sets(workout_session_exercise_id, set_number)`：查詢與唯一組號。

### 7.3 交易與併發

開始訓練、儲存組數、完成／取消都使用短交易。PostgreSQL 使用 `READ COMMITTED`，開始訓練會鎖定使用者資料列，最後由 partial unique index 防止同一使用者出現兩個 `in_progress` 場次。兩個請求同時送出時，最多一筆成功建立，另一筆應得到既有場次或衝突回應，不會產生兩筆 active session。

## 8. 管理員操作手冊

### 8.1 登入

課堂展示帳號：

```text
Email：admin@fittrack.local
密碼：Admin12345
```

這是展示用帳號，不可放真實個資。正式上線前應在 Render Environment 改成未公開密碼；容器重啟時 `bin/setup.php` 會同步 `ADMIN_BOOTSTRAP_PASSWORD`。

### 8.2 管理員可以做什麼

- 會員清單與狀態查看。
- 動作新增、停用、啟用與建立新版本。
- 修改訓練目標與身體部位說明。
- 查看資料庫 Driver、20 張表、資料筆數與關聯。
- 查看固定的唯讀 SQL 查詢範例。
- 查看 AI API 是否已設定；`AI_API_KEY` 不會顯示在瀏覽器。

### 8.3 動作修改的正確說法

管理員修改動作不是直接 UPDATE 舊的 `exercise_versions`。系統會建立新的 `exercise_version_id` 與遞增 `version_no`，`exercises.exercise_id` 保持穩定；舊課表和舊場次仍指向舊版本。

## 9. 備份、清理與維運

### 9.1 Session 清理

`bin/cleanup-expired.php`：

- 每批最多清理 500 筆過期 `user_sessions`。
- 清理超過 15 分鐘的 `login_failures`。
- 使用 PostgreSQL advisory lock 與 `FOR UPDATE SKIP LOCKED`，避免多個 Worker 重複清理。
- 日誌只輸出筆數與執行結果，不輸出 Token、密碼、完整連線字串或原始 IP。

### 9.2 每日備份

`.github/workflows/fittrack-maintenance.yml` 會：

1. 執行清理。
2. 產生 PostgreSQL `pg_dump`。
3. 還原到獨立 PostgreSQL 16 測試庫。
4. 比對 20 張表、25 條 FK、Migration 版本與每表筆數。
5. 驗證動作圖片 SHA-256 清單。
6. 加密備份並保留 7 天。

正式執行前需要在 GitHub Repository Secrets 設定：

```text
FITTRACK_DATABASE_URL
FITTRACK_BACKUP_KEY
```

## 10. 建議展示順序（約 8–10 分鐘）

1. **首頁／登入**：說明 PHP API、HttpOnly Cookie 與 PostgreSQL。
2. **編輯資料**：填寫基本資料、目標、訓練天數、時間與偏好部位。
3. **我的課表 → 電腦規劃**：展示兩次產生結果不同，並說明 `rules-v2-randomized`。
4. **我的課表 → 自己規劃**：自行挑動作、排序、調整組數與休息。
5. **開始訓練**：說明場次快照、總計時器、尚未儲存前休息計時器不啟動。
6. **儲存一組**：展示立即保存、休息倒數開始與進度更新。
7. **取消或完成**：說明 `cancelled` 可無組數、`completed` 至少一組。
8. **歷史／Dashboard**：說明場次快照、日期篩選、外加重量訓練量與徒手次數分開統計。
9. **動作庫**：搜尋 1,324 筆動作與圖片，說明版本不可覆寫。
10. **管理 → 資料庫系統**：展示 20 表、25 FK 與唯讀 SQL 查詢。

## 11. 老師可能問的問題與建議回答

### Q1：你的系統資料庫是什麼？為什麼選 PostgreSQL？

正式環境是 PostgreSQL 16，因為需要外鍵、Trigger、deferred constraint、partial unique index、advisory lock 與併發交易。SQLite 只用於本機快速預覽和測試，不能代表正式雲端資料庫。

### Q2：你的資料庫有幾張表？外鍵幾條？

20 張應用資料表、25 條外鍵，另外有 `schema_migrations` 記錄資料庫版本。可以從管理後台或 `tests/schema_consistency.py` 驗證。

### Q3：為什麼 users 和 user_auth 要拆開？

`users` 是個人與訓練設定，`user_auth` 是登入認證。拆開可以避免把密碼欄位混在個人資料，也能讓認證生命週期與個人資料分離；兩者用 `user_id` 1:1 關聯。

### Q4：哪裡有 M:N 關係？

使用者與身體部位是 M:N。一個使用者可選胸、背、腿等多個部位，一個部位也能被很多使用者選擇，因此用 `user_body_parts(user_id, body_part_id, priority)` 拆解。

### Q5：為什麼不把 body parts 存成 `Chest,Back,Legs` 字串？

那會違反 1NF，也不利於查詢、統計、外鍵驗證與排序。junction table 可以用 JOIN、GROUP BY、外鍵和複合主鍵正確管理。

### Q6：為什麼 exercises 還要拆 exercise_versions？

`exercises` 是穩定身份，`exercise_versions` 是會改變的描述內容。管理員修改動作時建立新版本，舊課表與歷史仍保留舊名稱、說明與圖片，避免歷史被現在資料污染。

### Q7：為什麼開始訓練還要複製 session snapshot？

課表是模板，場次是當天實際執行。若只存課表 ID，之後修改課表會讓舊訓練顯示錯誤；`workout_session_exercises` 保存當下版本、順序、組次、次數和休息，能完整重現歷史。

### Q8：使用者調整本次目標會不會修改原課表？

不會。只更新 `workout_session_exercises` 的本場目標，`plan_exercises` 原始模板不變；這是模板與執行實例分離。

### Q9：為什麼要有 `workout_session_plans`？

它把一次場次連回來源 `plan_day`，而且是一個場次一筆。這樣可以知道使用者當天執行哪一個課表日，也能讓 Trigger 驗證場次動作確實來自同一個 Day。

### Q10：如何避免同一個使用者同時開始兩次訓練？

應用層先鎖使用者資料列，資料庫再用 `uq_workout_sessions_user_active` partial unique index 限制 `status = 'in_progress'` 只能一筆。應用層和資料庫雙重保護，不能只相信前端。

### Q11：為什麼 completed 場次至少要一組？

「完成」代表有實際訓練成果；空場次應標記 cancelled 或保持進行中。資料庫用 deferred constraint trigger，在交易提交時檢查至少一筆 `workout_sets`，也防止透過刪除最後一組繞過規則。

### Q12：取消訓練和完成訓練差在哪裡？

完成必須有至少一組並納入統計；取消可以沒有組數，但會寫入 `ended_at` 與 `cancelled`，歷史可追蹤但不納入完成訓練統計。

### Q13：課表為什麼是封存不是刪除？

課表可能已被歷史場次引用。封存設定 `archived_at`，讓它不再出現在新的選擇清單，但保留來源與歷史參照，避免破壞資料鏈。

### Q14：你怎麼保護動作版本不被直接修改？

PostgreSQL Trigger `trg_exercise_versions_immutable` 直接拒絕 UPDATE／DELETE；管理員只能建立新版本。這是資料庫層保護，不是只靠前端按鈕隱藏。

### Q15：你怎麼計算訓練量？

外加重量訓練量是每組 `weight_kg × reps` 的總和；徒手動作重量為 0，不應被誤判成沒有訓練，所以 Dashboard 另外統計 `bodyweight_reps` 與完成次數。

### Q16：登入密碼怎麼保存？JWT 安全嗎？

密碼使用 bcrypt hash，不存明文。JWT 只存 `sub`、`jti`、`iat`、`exp`，並放在 HttpOnly Cookie；每次請求還要查 `user_sessions` 和 `user_auth`，所以登出或停用可以立即撤銷。管理員資格從 `admins` 即時查詢，不信任 JWT 內的 role。

### Q17：為什麼要 CSRF？

因為瀏覽器會自動帶 Cookie。系統要求同源、CSRF Header、Cookie Token 與 HMAC 簽章同時正確，避免其他網站偽造寫入要求。

### Q18：如何防止登入暴力嘗試？

失敗登入寫入 `login_failures`，IP 先以 `RATE_LIMIT_SECRET` 做 HMAC；15 分鐘內同來源前 20 次可記錄，第 21 次回 429 和 `Retry-After`。資料庫不可用時登入 fail closed 回 503。

### Q19：AI API 沒有 Key 還能用嗎？

可以。AI 是選配層，`AI_API_KEY` 空白時，使用者仍可使用自己規劃或規則式電腦規劃；AI 輸出也要再通過動作 ID、天數、組次、休息與時間規則驗證，不能讓模型直接寫入資料庫。

### Q20：電腦規劃怎麼避免每次一樣？

系統保留最近課表的動作身份，先把候選分成未近期使用、近期使用、已使用，再各自 shuffle；同一份課表還會去重，並維持八部位覆蓋與時間限制。版本記錄為 `rules-v2-randomized`。

### Q21：為什麼需要索引？你有哪些索引？

索引讓常用查詢不用掃完整張表，例如過期 Session、登入限流、最新體重、最新動作版本、使用者課表、訓練歷史和每組紀錄。索引要配合實際 WHERE、JOIN、ORDER BY，不能無限制新增。

### Q22：如果資料庫被直接 SQL 修改，系統還安全嗎？

重要規則已放在 FK、CHECK、UNIQUE、Trigger、partial unique index；直接 SQL 仍會被資料庫拒絕。應用層則負責權限、所有權、輸入格式與友善錯誤訊息，兩層一起保護。

### Q23：如何處理 Migration？

啟動時先檢查目前 Schema；舊版 SQLite 會先備份再升級。PostgreSQL 使用 `bin/migrate.php` 套用 migration，並以 `schema_migrations` 記錄版本；失敗時交易回滾，避免半套升級。

### Q24：如何備份與還原？

GitHub Actions 每日用 `pg_dump` 備份，還原到獨立 PostgreSQL 16 後比對 20 表、25 FK、版本與每表筆數，也驗證圖片 SHA-256；備份加密並保留 7 天。不能只保存一個資料庫 URL，因為那不是備份。

### Q25：本機 SQLite 和正式 PostgreSQL 會不會不一致？

兩者都有對應 Schema 和 SQLite 回歸測試，但 PostgreSQL 特有的 Trigger、deferred constraint、advisory lock、partial unique index，必須另外用 `tests/postgres_integrity.php` 在隔離 PostgreSQL 測試庫驗證，不能只用 SQLite 宣稱通過。

## 12. 常用查詢（展示時可用）

### 查詢 20 張應用表與 25 條 FK

```sql
SELECT COUNT(*) AS table_count
FROM pg_tables
WHERE schemaname = 'public' AND tablename <> 'schema_migrations';

SELECT COUNT(*) AS foreign_key_count
FROM information_schema.table_constraints
WHERE constraint_schema = 'public'
  AND constraint_type = 'FOREIGN KEY';
```

### 查某位使用者的課表與動作

```sql
SELECT
    wp.workout_plan_id,
    wp.plan_name,
    pd.day_number,
    pd.day_title,
    pe.exercise_order,
    ev.exercise_name,
    pe.target_sets,
    pe.target_reps,
    pe.rest_seconds
FROM workout_plans wp
JOIN plan_days pd ON pd.workout_plan_id = wp.workout_plan_id
JOIN plan_exercises pe ON pe.plan_day_id = pd.plan_day_id
JOIN exercise_versions ev ON ev.exercise_version_id = pe.exercise_version_id
WHERE wp.user_id = :user_id
  AND wp.archived_at IS NULL
ORDER BY wp.created_at DESC, pd.day_number, pe.exercise_order;
```

### 查某次訓練的實際組數

```sql
SELECT
    ws.workout_session_id,
    ws.status,
    ev.exercise_name,
    wse.exercise_order,
    wset.set_number,
    wset.weight_kg,
    wset.reps,
    wset.weight_kg * wset.reps AS set_volume
FROM workout_sessions ws
JOIN workout_session_exercises wse
  ON wse.workout_session_id = ws.workout_session_id
JOIN exercise_versions ev
  ON ev.exercise_version_id = wse.exercise_version_id
LEFT JOIN workout_sets wset
  ON wset.workout_session_exercise_id = wse.workout_session_exercise_id
WHERE ws.workout_session_id = :session_id
ORDER BY wse.exercise_order, wset.set_number;
```

### 查目前進行中的場次

```sql
SELECT workout_session_id, user_id, started_at
FROM workout_sessions
WHERE status = 'in_progress'
ORDER BY started_at DESC;
```
